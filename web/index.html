Cache economics · a field note

Prompt caching only pays when the cache gets read.

The first request is not a discount. You pay extra to write a stable prefix into the cache, then you hope later requests read it cheaply. If they do not, caching is just a premium. Most teams cannot tell which side they are on, because the proof is buried in API usage fields nobody tracks.

KCG Consulting · July 2026 · 5 min read
01 · How the pricing works

Every cached token follows one of three paths.

The bill depends on what happened to the prefix before this request arrived: no cache, a fresh write, or a cheap read.

Read
0.1×
The prefix was already there. This is the payoff.
Write · 5 min
1.25×
Store it for five minutes. Pay 25% more than normal input.
Write · 1 hour
2×
Store it for an hour. Pay double, and keep it twelve times longer.

Multipliers on the base input rate, checked against Anthropic's published pricing on 28 July 2026.

The real question is not whether caching is enabled. It is whether requests arrive soon enough to reuse what you already paid to store.

02 · What we found

Three popular agents leave the long cache unused.

We read the source for OpenHands, SWE-agent, and browser-use. All three use prompt caching. None of them can write the one-hour cache. Every call site emits {"type":"ephemeral"} with no ttl field, which means five minutes. There is no code path to the longer option.

That does not automatically make them expensive. It makes their cost depend on one thing: the gap between requests.

03 · When it matters

One hour only wins between five minutes and one hour.

Move the gap between requests. Under five minutes, both caches survive and the cheaper write wins. Over an hour, both caches expire and the cheaper write wins again. In the middle, the one-hour cache keeps reading while the five-minute cache keeps rebuilding.

This is arithmetic, not measurement. It assumes steady traffic and a stable prompt, and real traffic is neither. If your requests are almost always less than five minutes apart, the default cache is already doing the job and none of this applies to you.

05 · The comparison

The honest question is not whether caching beats no caching.

We used to say a gateway would place markers for you automatically, and that beating it was the bar. We checked, and that is not what LiteLLM does. Read at 1.83.9: markers are injected only where an operator configures cache_control_injection_points, and a request through it with none configured sends no cache_control at all. So the gateway arm is the request as shipped unless somebody has configured placement.

That correction cost us the flattering comparison, which is the point of making it. Comparing against nothing is how “up to 90%” gets printed, and inventing a competent baseline that does not exist is the same error wearing better clothes. The arms are still four over the same requests, replayed against a cache model whose lifetime we measured directly.

The last two are kept apart on purpose. Rolled together they produce one number that answers neither question, and they are not the same thing to ship: one is a setting, the other changes what the model reads first.

On our test workload, placement alone recovered 20%. Adding a single reordering — moving a session header below the stable text instead of above it — took it to 69%. That gap is the whole point: the marker had nowhere useful to go until the volatile block moved.

06 · Method

Two rules that make a number worth reading.

Every model here guesses in a few places: how long an entry really survives, whether an identical prefix reaches a machine that holds it, when a write becomes readable. Each guess is defensible on its own. The trouble is that all of them lean the same way, toward more cache hits, which flatters whoever is selling the cache advice.

So every projection runs twice, once with those guesses set generously and once set against us, and the headline is always the pessimistic end. A single number from a model that leans one way is not a finding.

The second rule is that a dollar figure about your traffic cannot be printed until it has been reconciled against a real invoice. Not warned about, not footnoted — withheld. Our reports render an unreconciled figure as [withheld], and the code refuses to turn one into a number. That rule exists because we kept catching ourselves publishing figures through paths that had skipped the check, and we are still finding them.

The calculator above is not covered by that rule and should not pretend to be. It is arithmetic on numbers you typed, at list prices, with no trace and no invoice behind it — a way to see the shape of the thing, not a claim about your bill.

Both rules cost us headline numbers. That is what they are for.

07 · The instrument

None of this is judgement calls in a spreadsheet.

The rules above are enforced by a working harness, not by remembering to apply them. It runs on your machine, reads usage fields and prompt structure rather than prompt text, and produces the report at the end of this section.

A capability registry, dated and sourced

Cache behaviour is not one thing. Bedrock wants longer-lived checkpoints before shorter ones; the direct API does not care. Minimum cacheable length moves between model generations and does not move in one direction — 512 tokens on Opus 5, 1,024 on Opus 4.8, 4,096 on Opus 4.6 and Haiku 4.5. Below that line the request is processed uncached and no error is returned. You cannot reason your way to these; they have to be looked up.

Three checks that need nothing from you

No traffic, no logs, no API key. They read a request you are about to send and answer whether the provider will silently ignore your markers. Real output:

The first one is the point. A checker that answers confidently when it cannot tell gets switched off within a week, and then catches nothing. Abstaining is a result.
